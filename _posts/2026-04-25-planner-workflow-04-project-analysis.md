# 4. 프로젝트 분석서로 수행 구조 잡기

프로젝트 분석서는 Project Profile보다 한 단계 더 깊게 들어가 실제 수행 구조를 정리하는 문서입니다. 진행 배경, 개발 범위, 개발 순서, 파견 여부, 업무 배분, 일정, 사양, 주요 이슈를 연결해 봅니다.

이 문서는 제안 단계에서도 쓰이고, 착수 직후 팀이 같은 그림을 보기 위해서도 유용합니다.

## 프로젝트 분석서의 구성

| 항목 | 정리할 내용 |
| --- | --- |
| 진행 배경 | 고객이 프로젝트를 추진하는 이유 |
| 개발 범위 | 구축할 서비스, 화면, 기능, 콘텐츠 |
| 개발 순서 | 어떤 영역부터 분석하고 설계할지 |
| 진행 현황 | 이미 진행된 회의, 자료, 의사결정 |
| 파견 여부 | 상주 또는 비상주 수행 방식 |
| 업무 배분 | 고객사, 수행사, 외주사 역할 |
| 개발 PM | 일정과 품질을 관리할 책임 구조 |
| 개발 일정 | 분석, 설계, 구현, 검수, 오픈 일정 |
| 개발 사양 | 환경, 연동, 권한, 주요 기능 |
| 주요 이슈 | 일정, 범위, 데이터, 승인, 리스크 |

## 범위는 포함과 제외를 함께 적기

범위를 쓸 때는 포함되는 것만 적으면 부족합니다. 나중에 갈등이 생기는 부분은 대개 “당연히 포함된 줄 알았다”에서 시작합니다.

| 범위 구분 | 예시 |
| --- | --- |
| 포함 | IA, 화면설계, 디자인, 퍼블리싱, 개발, 검수 |
| 조건부 포함 | 기존 데이터 정리, 외부 시스템 연동, 운영 매뉴얼 |
| 제외 | 콘텐츠 원고 작성, 촬영, 번역, 별도 솔루션 비용 |
| 추후 협의 | 관리자 통계, 마케팅 자동화, 추가 캠페인 페이지 |

## 업무 배분을 문장으로 남기기

역할표만으로는 부족할 때가 많습니다. 특히 고객사와 수행사가 함께 해야 하는 일은 문장으로 남겨야 합니다.

| 업무 | 고객사 | 수행사 |
| --- | --- | --- |
| 요구사항 확정 | 업무 기준과 승인 제공 | 요구사항 정리와 영향 분석 |
| 콘텐츠 준비 | 원고, 이미지, 정책 제공 | 등록 구조와 검수 기준 제안 |
| 디자인 검토 | 브랜드 기준 확인 | 시안 제작과 수정 반영 |
| 개발 검수 | 업무 기준 확인 | 오류 수정과 기술 검증 |
| 오픈 준비 | 운영 승인 | 배포, 모니터링, 장애 대응 |

## 주요 이슈를 관리 항목으로 바꾸기

이슈는 적는 것보다 관리 가능한 형태로 바꾸는 것이 중요합니다.

| 이슈 | 관리 항목 |
| --- | --- |
| 자료 제공이 늦음 | 자료 제공 마감일과 대체안 |
| 승인자가 많음 | 승인 단계와 최종 결정권자 |
| 기존 시스템 정보가 부족함 | 기술 인터뷰 일정 |
| 일정이 짧음 | 우선순위와 단계 오픈 기준 |
| 외부 연동이 있음 | 담당자, 테스트 환경, 실패 시 대응 |

{: .note }
프로젝트 분석서는 “잘될 것 같다”는 감각을 “어떤 조건이면 잘될 수 있다”로 바꾸는 문서입니다.

## 분석 회의에서 확인할 것

프로젝트 분석서는 혼자 책상에서 완성하기 어렵습니다. 기획, 디자인, 개발, 영업 또는 운영 담당자가 함께 보고 빈칸을 채워야 합니다.

| 참여자 | 확인할 내용 |
| --- | --- |
| PM | 일정, 범위, 고객 커뮤니케이션, 의사결정 구조 |
| 기획 | 요구사항, 화면 수, 정책 복잡도, 콘텐츠 |
| 디자인 | 브랜드 기준, 시안 수, 디자인 시스템 필요 여부 |
| 개발 | 연동, 권한, 데이터, 관리자, 배포 환경 |
| 운영 | 오픈 후 문의, 콘텐츠 수정, 운영 프로세스 |

## 업무 배분을 R&R로 정리하기

역할을 말로 합의하면 나중에 빠지는 일이 생깁니다. 최소한 다음 정도는 표로 남겨둡니다.

| 업무 | 책임 | 협의 | 승인 |
| --- | --- | --- | --- |
| 요구사항 정리 | 기획 | PM, 고객 실무자 | 고객 승인자 |
| IA와 화면설계 | 기획 | 디자인, 개발 | PM |
| 디자인 시안 | 디자인 | 기획, 고객 실무자 | 고객 승인자 |
| 기능 개발 | 개발 | 기획, PM | PM |
| 콘텐츠 등록 | 고객 또는 운영 | 기획 | 고객 실무자 |
| 검수 | PM | 전체 TF | 고객 승인자 |

## 리스크 등급 붙이기

이슈 목록만 적으면 우선순위가 흐려집니다. 영향도와 가능성을 기준으로 등급을 붙이면 관리가 쉬워집니다.

| 리스크 | 영향도 | 가능성 | 대응 |
| --- | --- | --- | --- |
| 고객 자료 제공 지연 | 높음 | 높음 | 자료 마감일과 대체 콘텐츠 정의 |
| 외부 시스템 연동 정보 부족 | 높음 | 중간 | 기술 담당자 인터뷰 일정 확보 |
| 디자인 승인자 다수 | 중간 | 높음 | 승인 라인과 최종 결정권자 확정 |
| 데이터 정제 범위 불명확 | 높음 | 중간 | 이전 대상과 제외 대상을 표로 분리 |

## 착수 전에 남겨야 할 결론

| 결론 | 문장 예시 |
| --- | --- |
| 우선순위 | 1차 오픈은 사용자 핵심 흐름과 관리자 필수 기능에 집중한다 |
| 제외 범위 | 기존 콘텐츠 원고 작성과 이미지 제작은 고객사 제공 범위로 둔다 |
| 일정 전제 | 외부 연동 정보가 착수 후 1주 내 제공된다는 전제로 일정을 산정한다 |
| 검수 전제 | 검수는 개발 검수 1회, 고객 검수 1회, 재검수 1회로 운영한다 |

## 다음 글로 이어지는 질문

수행 구조를 잡았다면 필요한 사람을 요청해야 합니다. 다음 글에서는 인력 배치서를 통해 역할과 시점을 정리합니다.
