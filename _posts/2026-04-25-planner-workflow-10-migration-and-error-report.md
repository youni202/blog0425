# 10. 데이터 이전 계획서와 오류 리포트로 오픈 마무리하기

오픈 전후에는 작은 누락도 큰 장애처럼 보일 수 있습니다. 그래서 데이터 이전 계획서와 오류 리포트가 필요합니다.

데이터 이전 계획서는 개발 서버의 프로그램, 이미지, 데이터 등을 운영 서버로 옮기는 절차를 정리하고, 오류 리포트는 오픈 후 발견된 문제를 추적합니다.

## 데이터 이전 계획서 기본 항목

| 항목 | 작성 내용 |
| --- | --- |
| 목적 | 외부 오픈을 위해 운영 환경으로 이전 |
| 이전 대상 | 프로그램 모듈, 이미지, 콘텐츠, 설정 |
| 이전 날짜 | 실제 이전 예정일 |
| 이전 시간 | 서비스 영향이 적은 시간대 |
| 서비스 상황 | 정지, 일부 기능 정지, 정상 서비스 |
| 정지 소요시간 | 예상 점검 시간 |
| 사용자 알림 | 점검 페이지, 팝업, 공지 |

| 순서 | 작업 | 체크 |
| --- | --- | --- |
| 1 | 점검 안내 페이지 제작 |  |
| 2 | 이전 대상 확인 |  |
| 3 | 웹서버 또는 관련 서비스 중지 |  |
| 4 | 점검 안내 페이지 적용 |  |
| 5 | 점검 안내 노출 확인 |  |
| 6 | 프로그램과 이미지 이전 |  |
| 7 | 데이터 이전 |  |
| 8 | 설치 검수 진행 |  |
| 9 | 오류 수정 |  |
| 10 | 운영 페이지 전환 |  |
| 11 | 서비스 재시작 |  |
| 12 | 오픈 후 검수 |  |

## 사용자 알림 문구

서비스 영향이 있다면 사용자가 상황을 이해할 수 있게 안내해야 합니다.

| 상황 | 안내 방향 |
| --- | --- |
| 전체 점검 | 점검 시간과 재개 예정 시간 표시 |
| 일부 기능 제한 | 제한되는 기능과 대체 방법 안내 |
| 정상 서비스 중 이전 | 오류 가능성과 문의 채널 안내 |

## 오류 리포트 구조

| 항목 | 작성 내용 |
| --- | --- |
| NO | 오류 번호 |
| 오류 경로 | 메뉴 또는 화면 경로 |
| 오류 내용 | 사용자가 본 문제 |
| 처리 사항 | 처리 중, 처리 완료, 보류 |
| 완료일 | 수정 완료 날짜 |

## 오류 관리 예시

| NO | 오류 경로 | 오류 내용 | 처리 사항 | 완료일 |
| --- | --- | --- | --- | --- |
| 1 | 메인 > 공지사항 | 문구 오타 발견 | 처리 완료 | D+1 |
| 2 | 서브 > 이미지 영역 | 이미지가 노출되지 않음 | 처리 중 |  |
| 3 | 회원 > 로그인 | 특정 계정 로그인 실패 | 원인 확인 |  |

## 오픈 후 모니터링

오픈 직후에는 최소 1일차, 2일차, 3일차로 나눠 오류를 관리하는 것이 좋습니다.

| 기간 | 확인 내용 |
| --- | --- |
| 1일차 | 핵심 기능, 접속, 결제/신청, 관리자 |
| 2일차 | 콘텐츠, 이미지, 링크, 사용자 문의 |
| 3일차 | 반복 오류, 지연 처리, 운영 이관 |

{: .note }
오픈은 끝이 아니라 운영으로 넘어가는 순간입니다. 이전 계획과 오류 리포트가 있어야 프로젝트가 안정적으로 닫힙니다.

## 시리즈 마무리

기획자의 문서는 각각 따로 존재하지 않습니다. 프로젝트 프로파일에서 시작한 정보가 제안 분석서, 프로젝트 분석서, 계약 조건, 검수 계획서, 오픈 문서까지 이어질 때 프로젝트 관리가 훨씬 단단해집니다.
