# 10. 데이터 이전 계획서와 오류 리포트로 오픈 마무리하기

오픈 전후에는 작은 누락도 큰 장애처럼 보일 수 있습니다. 그래서 데이터 이전 계획서와 오류 리포트가 필요합니다.

데이터 이전 계획서는 개발 서버의 프로그램, 이미지, 데이터 등을 운영 서버로 옮기는 절차를 정리하고, 오류 리포트는 오픈 후 발견된 문제를 추적합니다.

## 데이터 이전 계획서 기본 항목

| 항목 | 작성 내용 |
| --- | --- |
| 목적 | 외부 오픈을 위해 운영 환경으로 이전 |
| 이전 대상 | 프로그램 모듈, 이미지, 콘텐츠, 설정 |
| 이전 날짜 | 실제 이전 예정일 |
| 이전 시간 | 서비스 영향이 적은 시간대 |
| 서비스 상황 | 정지, 일부 기능 정지, 정상 서비스 |
| 정지 소요시간 | 예상 점검 시간 |
| 사용자 알림 | 점검 페이지, 팝업, 공지 |

## 사용자 알림 문구

서비스 영향이 있다면 사용자가 상황을 이해할 수 있게 안내해야 합니다.

| 상황 | 안내 방향 |
| --- | --- |
| 전체 점검 | 점검 시간과 재개 예정 시간 표시 |
| 일부 기능 제한 | 제한되는 기능과 대체 방법 안내 |
| 정상 서비스 중 이전 | 오류 가능성과 문의 채널 안내 |

## 오류 리포트 구조

| 항목 | 작성 내용 |
| --- | --- |
| NO | 오류 번호 |
| 오류 경로 | 메뉴 또는 화면 경로 |

| 처리 사항 | 처리 중, 처리 완료, 보류 |
| 완료일 | 수정 완료 날짜 |

## 오픈 후 모니터링

오픈 직후에는 최소 1일차, 2일차, 3일차로 나눠 오류를 관리하는 것이 좋습니다.

| 기간 | 확인 내용 |
| --- | --- |
| 1일차 | 핵심 기능, 접속, 결제/신청, 관리자 |
| 2일차 | 콘텐츠, 이미지, 링크, 사용자 문의 |
| 3일차 | 반복 오류, 지연 처리, 운영 이관 |

{: .note }
오픈은 끝이 아니라 운영으로 넘어가는 순간입니다. 이전 계획과 오류 리포트가 있어야 프로젝트가 안정적으로 닫힙니다.

## 오픈 전날 체크리스트

| 확인 | 항목 |
| --- | --- |
|  | 이전 대상 파일과 데이터 목록이 확정되었는가 |
|  | 운영 서버 접속 권한과 배포 권한이 준비되었는가 |
|  | 점검 안내 문구와 노출 방식이 승인되었는가 |
|  | 롤백 기준과 담당자가 정해졌는가 |
|  | 오픈 후 모니터링 담당자가 시간대별로 배정되었는가 |
|  | 고객사와 수행사의 비상 연락망이 공유되었는가 |

## 롤백 기준도 정해두기

오픈 계획에는 성공 절차뿐 아니라 되돌리는 기준도 있어야 합니다.

| 상황 | 판단 기준 | 조치 |
| --- | --- | --- |
| 접속 불가 | 주요 화면 접속이 일정 시간 이상 실패 | 이전 버전 복구 |
| 핵심 기능 장애 | 신청, 결제, 로그인 등 핵심 흐름 실패 | 기능 비활성 또는 롤백 |
| 데이터 오류 | 이전 데이터 누락 또는 매핑 오류 | 이전 중지 후 원인 확인 |
| 외부 연동 장애 | 인증, 알림, API 연동 실패 | 연동 담당자 호출 및 대체 안내 |

## 오류 우선순위

오픈 후 오류는 모두 급해 보이지만, 처리 순서를 나눠야 합니다.

| 우선순위 | 기준 | 예시 |
| --- | --- | --- |
| 긴급 | 서비스 이용을 막음 | 로그인 불가, 신청 불가, 결제 실패 |
| 높음 | 주요 기능에 영향을 줌 | 관리자 저장 실패, 핵심 이미지 미노출 |
| 보통 | 사용은 가능하지만 수정 필요 | 문구 오타, 일부 링크 오류 |
| 낮음 | 운영 개선 항목 | 정렬 방식 개선, 안내 문구 보완 |

## 오류 리포트 작성 예시

| NO | 우선순위 | 오류 경로 | 오류 내용 | 담당 | 상태 |
| --- | --- | --- | --- | --- | --- |
| 1 | 긴급 | 로그인 | 정상 계정으로 로그인 시도 시 오류 메시지 노출 | 개발 | 처리 중 |
| 2 | 높음 | 관리자 > 게시물 | 이미지 업로드 후 썸네일 미노출 | 개발 | 수정 완료 |
| 3 | 보통 | 메인 | 공지사항 문구 오타 | 운영 | 처리 완료 |

## 운영 이관 메모

프로젝트를 닫기 전에는 운영자가 알아야 할 내용을 따로 남겨야 합니다.

| 항목 | 내용 |
| --- | --- |
| 운영 계정 | 관리자 URL, 계정 발급 방식, 권한 구분 |
| 반복 업무 | 게시물 등록, 배너 교체, 통계 확인 |
| 장애 대응 | 문의 채널, 담당자, 응답 기준 |
| 남은 과제 | 오픈 후 처리하기로 한 보류 오류 |
| 정기 점검 | 로그 확인, 백업, 인증서 만료일 |

## 시리즈 마무리

기획자의 문서는 각각 따로 존재하지 않습니다. 프로젝트 프로파일에서 시작한 정보가 제안 분석서, 프로젝트 분석서, 계약 조건, 검수 계획서, 오픈 문서까지 이어질 때 프로젝트 관리가 훨씬 단단해집니다.
