# 3. 제안 분석서로 제안 여부 판단하기

제안 분석서는 들어온 의뢰를 보고 “제안할 것인가, 한다면 어떤 방향으로 할 것인가”를 판단하기 위한 문서입니다.

좋은 제안은 열심히 만드는 것만으로 완성되지 않습니다. 고객의 기대, 일정, 예산, 경쟁 상황, 내부 투입 가능성을 먼저 읽어야 합니다.

## 제안 분석서의 기본 항목

| 구분 | 확인 내용 |
| --- | --- |
| 고객사 정보 | 회사, 담당 부서, 의사결정 구조 |
| 프로젝트 정보 | 사업명, 구분, 범위, 배경 |
| 의뢰 구분 | 신규 제안, 운영 제안, 추가 제안 |
| 업체 선정 방식 | 경쟁 입찰, 제한 입찰, 지명 |
| RFP 여부 | 공식 문서 유무와 해석 필요 항목 |
| 제안 일정 | 제출일, PT일, 질의응답 일정 |
| 우선순위 | 가격, 일정, 품질, 안정성, 레퍼런스 |
| 예산 | 공개 예산, 예상 예산, 적정성 |
| 파견 여부 | 상주 요구와 내부 대응 가능성 |
| 운영 대행 여부 | 구축 후 운영 범위 포함 여부 |

## 제안하기 전에 봐야 할 신호

| 질문 | 왜 중요한가 |
| --- | --- |
| 예산과 범위가 맞는가? | 무리한 범위는 수행 리스크로 이어짐 |
| 제안 준비 시간이 충분한가? | 전략, 화면, 견적의 품질을 좌우함 |
| 고객의 성공 기준이 분명한가? | 제안 메시지를 잡는 기준이 됨 |
| 내부 인력 투입이 가능한가? | 제안 후 수주해도 수행이 어려울 수 있음 |
| 경쟁사가 이미 정해져 있지는 않은가? | 들러리 제안 가능성을 줄여야 함 |

## 제안 전략으로 바꾸기

분석서의 목적은 정보를 모으는 데서 끝나지 않습니다. 분석한 내용을 제안 전략으로 바꿔야 합니다.

| 분석 결과 | 제안 전략 |
| --- | --- |
| 고객이 일정 단축을 중요하게 봄 | 단계별 오픈, 우선순위 기반 구축안 제시 |
| 운영 안정성이 중요함 | 운영 프로세스와 대응 체계 강조 |
| 브랜드 경험이 중요함 | 콘텐츠 구조와 디자인 방향을 전면에 배치 |
| 예산 제약이 큼 | 필수 범위와 옵션 범위를 분리 |
| 내부 승인 라인이 복잡함 | 의사결정자별 관심사를 나눠 설명 |

## 제안 분석서 작성 팁

제안 분석서는 “우리에게 유리한 이야기”만 적는 문서가 아닙니다. 불리한 조건과 리스크를 적어야 실제 의사결정에 쓸 수 있습니다.

| 리스크 | 대응 방향 |
| --- | --- |
| 준비 기간이 짧음 | 제안 범위를 압축하고 핵심 화면에 집중 |
| RFP가 모호함 | 질의 목록을 먼저 정리 |
| 예산이 낮음 | 우선 구축 범위를 분리 |
| 파견 요구가 있음 | 가능한 역할과 불가능한 역할을 명확히 구분 |

{: .tip }
제안 분석서에는 “이 제안은 왜 이길 수 있는가”와 “이 제안은 왜 위험한가”가 함께 있어야 합니다.

## Go 또는 No-Go 판단하기

모든 제안을 다 하는 조직은 오래 버티기 어렵습니다. 제안 분석서에는 참여 여부를 판단할 수 있는 기준이 있어야 합니다.

| 판단 항목 | Go에 가까운 신호 | No-Go를 검토할 신호 |
| --- | --- | --- |
| 예산 | 범위 대비 현실적 | 예산은 낮고 요구 범위는 큼 |
| 일정 | 제안과 수행 준비 시간이 있음 | 제출까지 시간이 극단적으로 짧음 |
| 관계 | 고객의 문제를 직접 들을 수 있음 | 담당자 접촉이 제한되고 정보가 부족함 |
| 경쟁 | 차별화 포인트가 있음 | 이미 내정된 업체가 의심됨 |
| 수행 | 내부 인력 투입 가능 | 수주해도 수행 인력이 없음 |

## 제안 전략 문장 만들기

분석한 내용을 제안서 첫 장의 방향으로 바꾸려면 한 문장으로 정리해 봅니다.

| 분석 내용 | 전략 문장 |
| --- | --- |
| 고객은 운영 효율을 가장 중요하게 봄 | 이번 제안은 구축보다 운영자가 매일 편하게 쓰는 관리 구조를 중심에 둔다 |
| 일정이 짧고 오픈일이 고정됨 | 1차 오픈 범위를 명확히 줄이고, 확장 기능은 2차 로드맵으로 제안한다 |
| 브랜드 표현이 중요함 | 화면 개편보다 브랜드 경험의 일관성을 제안의 핵심 메시지로 잡는다 |
| 예산이 빠듯함 | 필수 기능과 선택 기능을 분리해 고객이 결정할 수 있게 한다 |

## 제안 전 질의 목록

RFP를 받았더라도 모호한 부분은 반드시 질문으로 바꿔야 합니다.

| 영역 | 질문 |
| --- | --- |
| 범위 | 기존 데이터 이전과 콘텐츠 등록은 어느 쪽이 담당하나요? |
| 일정 | 중간 보고와 최종 PT 외에 내부 승인 일정이 있나요? |
| 기술 | 연동 대상 시스템의 담당자와 테스트 환경이 준비되어 있나요? |
| 운영 | 오픈 후 운영 대행 범위와 응답 시간이 정해져 있나요? |
| 평가 | 업체 선정 시 가장 높은 비중을 차지하는 기준은 무엇인가요? |

## 흔한 실수

| 실수 | 결과 | 보완 방법 |
| --- | --- | --- |
| RFP 문구를 그대로 믿음 | 숨은 범위가 뒤늦게 드러남 | 모호한 단어를 질문으로 바꿈 |
| 제안 전략 없이 목차부터 만듦 | 제안서가 설명서처럼 보임 | 먼저 이길 수 있는 메시지를 정함 |
| 견적을 마지막에 맞춤 | 범위와 금액이 어긋남 | 초반부터 필수/선택 범위를 나눔 |
| 리스크를 숨김 | 수주 후 수행 단계에서 터짐 | 내부 검토용 리스크를 별도로 기록 |

## 다음 글로 이어지는 질문
