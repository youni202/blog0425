# 1. 10년차 IT 서비스 기획자의 하루

IT 서비스 기획자의 하루는 문서를 쓰는 시간만으로 채워지지 않습니다. 메시지를 확인하고, 일정을 조정하고, 회의에서 결정된 내용을 기록하고, 개발자와 디자이너가 움직일 수 있도록 맥락을 정리하는 일이 반복됩니다.

이 글은 기획자의 일상 업무를 시간대별로 정리한 기본 흐름입니다.

## 하루 업무 흐름

| 시간 | 업무 | 핵심 행동 | 도구 예시 |
| --- | --- | --- | --- |
| 출근 전 | 팀 상태 확인 | 급한 메시지와 공유 사항 확인 | Teams |
| 09:30 | 메일과 일정 확인 | 회의, 요청, 마감 일정 점검 | Outlook |
| 09:45 | 할 일 정리 | 우선순위와 진행 상태 재정렬 | Planner, To Do |
| 10:00 | 기획서 작성 | 레퍼런스 조사, 경쟁사 분석, 화면 흐름 정리 | PowerPoint, Copilot |
| 14:30 | 회의 | 의사결정, 이슈 확인, 다음 액션 합의 | Teams |
| 16:30 | 회의록 작성 | 결정 사항과 담당자, 기한 기록 | Word |
| 16:30-18:30 | 협업 정리 | 개발 문의, 디자인 피드백, 문서 보완 | PowerPoint, Teams |
| 18:30 | 일일 보고 | 오늘 한 일, 이슈, 내일 할 일 정리 | Word |

## 기획자의 하루에서 중요한 것

가장 중요한 것은 “내가 무엇을 했는가”보다 “다음 사람이 무엇을 하면 되는가”입니다. 회의록, 기획서, 할 일 목록은 모두 다음 행동을 분명하게 만들기 위한 도구입니다.

| 상황 | 기록해야 할 것 |
| --- | --- |
| 회의가 끝났을 때 | 결정 사항, 보류 사항, 담당자, 기한 |
| 요구사항이 바뀌었을 때 | 변경 전후 내용, 영향 범위, 확인자 |
| 개발 문의가 왔을 때 | 질문, 답변, 근거 화면, 후속 조치 |
| 일정이 밀릴 때 | 원인, 영향 받는 업무, 조정안 |

## 회의록 기본 구조

회의록은 길게 쓰는 문서가 아니라 나중에 다시 열었을 때 결정의 맥락을 복원하는 문서입니다.

| 항목 | 작성 내용 |
| --- | --- |
| 회의 정보 | 날짜, 시간, 장소, 주관 부서, 참석자 |
| 회의 주제 | 논의할 안건 목록 |
| 논의 내용 | 안건별 주요 의견과 쟁점 |
| 결정 사항 | 확정된 내용 |
| 액션 아이템 | 담당자, 해야 할 일, 기한 |

{: .tip }
회의록을 쓸 때는 “논의했다”에서 멈추지 말고 “누가 언제까지 무엇을 한다”까지 적어야 합니다. 그래야 회의가 업무로 이어집니다.

## 다음 글로 이어지는 질문

하루 업무 흐름이 안정되면, 새 프로젝트를 처음 만났을 때 무엇부터 확인해야 하는지가 중요해집니다. 다음 글에서는 프로젝트의 기본 정보를 정리하는 Project Profile을 다룹니다.
