# 8. 검수 계획서로 검수의 기준 세우기

검수 계획서는 검수 범위, 일정, 환경, 방법, 담당자를 정의해 검수 단계를 효율적으로 수행하기 위한 문서입니다.

검수는 마지막에 “한번 봐주세요”라고 요청하는 일이 아닙니다. 무엇을 기준으로 완료를 판단할지 미리 합의하는 과정입니다.

## 검수 용어 정리

| 용어 | 의미 |
| --- | --- |
| 개발 검수 | 수행사가 구현 기능이 정상 동작하는지 확인 |
| 고객 검수 | 고객이 수행 범위에 맞게 기능이 동작하는지 확인 |
| 검수 시나리오 | 기능을 어떤 방법으로 검수할지 문서화한 것 |
| 산출물 검수 | 정의된 산출물이 모두 제출되었는지 확인 |

## 검수 계획서 구성

| 항목 | 작성 내용 |
| --- | --- |
| 검수 개요 | 목적과 용어 정의 |
| 검수 범위 | 기획, 디자인, 개발, 콘텐츠, 산출물 |
| 검수 환경 | 개발, 스테이징, 운영 등 테스트 위치 |
| 검수 담당 | 수행사, 고객사, 부서별 테스터 |
| 검수 일정 | 테스트 기간, 수정 기간, 재검수 기간 |
| 검수 확인 | 완료 기준과 승인 방식 |
| 예외 약정 | 검수 제외 항목, 추후 처리 항목 |

## 검수 범위 나누기

| 부문 | 검수 대상 |
| --- | --- |
| 기획 | 화면설계서, 정책, 콘텐츠 구조 |
| 디자인 | 디자인 시스템, 주요 화면, 이미지 원본 |
| 퍼블리싱 | HTML, 반응형, 브라우저 호환성 |
| 개발 | 기능, 관리자, 권한, 연동 |
| 콘텐츠 | 오타, 이미지, 링크, 게시물 |
| 산출물 | 매뉴얼, 소스, 계정, 운영 문서 |

## 누가 무엇을 검수할지 정하기

검수 담당을 “전체”로만 적으면 실제로는 아무도 책임지지 않는 항목이 생깁니다.

| 역할 | 담당 검수 |
| --- | --- |
| PM | 전체 일정, 범위, 이슈 관리 |
| 기획자 | 정책, 화면 흐름, 문구 |
| 디자이너 | 디자인 반영, 이미지 품질 |
| 개발자 | 기능 동작, 오류 수정 |
| 고객 실무자 | 업무 기준, 콘텐츠, 운영 가능성 |
| 고객 승인자 | 최종 완료 승인 |

## 검수 일정 예시

| 기간 | 활동 |
| --- | --- |
| D-7 | 검수 범위와 담당자 확정 |
| D-5 | 검수 시나리오 공유 |
| D-3 | 개발 검수와 1차 오류 수정 |
| D-2 | 고객 검수 진행 |
| D-1 | 재검수와 오픈 승인 |
| D-Day | 오픈 후 모니터링 |

{: .note }
검수 계획서는 오류를 찾기 위한 문서이면서 동시에 완료 기준을 합의하기 위한 문서입니다.

## 검수 계획을 세우는 순서

검수 계획서는 검수 직전에 쓰면 늦습니다. 설계가 어느 정도 마무리되는 시점부터 범위와 담당자를 잡아두는 것이 좋습니다.

| 순서 | 작업 | 결과 |
| --- | --- | --- |
| 1 | 수행 범위와 산출물 목록 확인 | 검수 대상 후보 |
| 2 | 개발 검수와 고객 검수 분리 | 책임 범위 명확화 |
| 3 | 부서별 테스터 지정 | 누락 없는 검수 담당 |
| 4 | 검수 환경과 계정 준비 | 실제 테스트 가능 상태 |
| 5 | 오류 접수 방식 정의 | 이슈 관리 기준 |
| 6 | 완료 승인 방식 합의 | 검수 종료 기준 |

## 검수 대상 예시

| 영역 | 검수 항목 |
| --- | --- |
| 사용자 화면 | 주요 메뉴, 신청/조회/검색, 반응형 화면 |
| 관리자 | 로그인, 권한, 목록, 등록/수정/삭제, 엑셀 다운로드 |
| 콘텐츠 | 문구, 이미지, 링크, 약관, 개인정보 처리방침 |
| 연동 | 인증, 결제, 알림, 외부 API, 배치 |
| 성능/환경 | 주요 브라우저, 모바일, 운영 도메인, SSL |
| 산출물 | 화면설계서, 디자인 원본, 운영 매뉴얼, 계정 정보 |

## 오류 접수 규칙

검수에서 가장 중요한 운영 규칙은 오류를 어디에 어떻게 적을지입니다.

| 규칙 | 설명 |
| --- | --- |
| 한 줄에 한 오류 | 여러 오류를 한 셀에 몰아넣지 않기 |
| 재현 경로 필수 | 어디서 어떻게 발생했는지 적기 |
| 기대 결과 작성 | 정상이라면 어떤 결과여야 하는지 적기 |
| 화면 캡처 첨부 | 설명만으로 부족한 오류는 이미지 첨부 |
| 상태값 통일 | 신규, 처리 중, 수정 완료, 재검수 완료 등으로 관리 |

## 검수 종료 기준

검수 종료 기준이 없으면 오류가 0개가 될 때까지 끝나지 않는 분위기가 생깁니다. 프로젝트 특성에 맞는 종료 기준을 미리 합의해야 합니다.

| 기준 | 예시 |
| --- | --- |
| 필수 기능 | 핵심 사용자 흐름과 관리자 필수 기능이 정상 동작 |
| 치명 오류 | 서비스 이용을 막는 오류 0건 |
| 일반 오류 | 오픈 후 처리 가능한 오류는 목록화하고 담당자 지정 |
| 산출물 | 운영에 필요한 계정, 매뉴얼, 원본 파일 인수 |
| 승인 | 고객 담당자의 검수 완료 확인 |

## 흔한 실수

| 실수 | 문제 | 보완 방법 |
| --- | --- | --- |
| 검수 담당을 전체로 둠 | 실제 검수 누락 발생 | 메뉴별 담당자 지정 |
| 오류 접수 양식이 없음 | 처리 상태 추적 불가 | 오류 리포트 양식 사전 공유 |
| 테스트 계정을 늦게 준비 | 검수 첫날 시간을 잃음 | D-3까지 계정과 권한 확인 |
| 산출물 검수를 빼먹음 | 오픈 후 운영 자료 부족 | 기능 검수와 산출물 검수를 분리 |

## 다음 글로 이어지는 질문

검수 계획이 세워졌다면 이제 실제로 테스트할 수 있는 절차가 필요합니다. 다음 글에서는 검수 시나리오를 작성하는 방법을 다룹니다.
